# Research: Local Game Session

**Date**: 2026-06-10

## 1. Next.js Bootstrap and Runtime

**Decision**: Target Next.js 16.2.x with React 19, TypeScript strict mode, App Router, `src/`, npm,
ESLint, Tailwind, and Node.js 24 LTS. Generate a temporary empty app with `create-next-app@latest`
and merge it into the non-empty Spec Kit repository root.

**Rationale**: Current Next.js documentation lists 16.2.2, requires Node 20.9 or newer, and documents
CLI flags for TypeScript, ESLint, Tailwind, App Router, `src`, npm, empty templates, disabled git, and
agent-file control. Node 24 is installed locally and is also supported by Playwright. A temporary
bootstrap preserves `.specify/`, `specs/`, and the existing `AGENTS.md`.

**Alternatives considered**:

- Run `create-next-app` directly in `.`: rejected because the repository is already non-empty and
  contains files that must not be overwritten.
- Hand-author every Next.js config file: viable, but rejected because the current generator provides
  safer version-aligned defaults.
- Pages Router or monorepo: rejected by project constraints and unnecessary scope.

**Sources**:

- https://nextjs.org/docs/app/getting-started/installation
- https://nextjs.org/docs/app/api-reference/cli/create-next-app
- https://nodejs.org/en/about/previous-releases

## 2. Tailwind CSS

**Decision**: Use Tailwind CSS 4 generated by current `create-next-app`, retaining the PostCSS plugin
and `@import "tailwindcss"` global stylesheet pattern.

**Rationale**: The current official Next.js guide installs `tailwindcss`, `@tailwindcss/postcss`, and
`postcss`, then imports Tailwind from the global stylesheet. `create-next-app --tailwind` provides
these aligned defaults.

**Alternatives considered**:

- Tailwind 3 configuration: rejected because it is legacy guidance for a new project.
- CSS Modules only: rejected because Tailwind is an explicit project choice.

**Source**: https://tailwindcss.com/docs/installation/framework-guides/nextjs

## 3. shadcn/ui

**Decision**: Initialize shadcn/ui after the Next.js files exist using `npx shadcn@latest init`, then
add only generic primitives actually used, initially Button, Select, and Alert where appropriate.
Keep the board, cards, key, QR presentation, and starting-team indicator custom.

**Rationale**: The official existing-project flow expects Tailwind and the `@/*` alias, both supplied
by the chosen bootstrap. Selective copied components avoid a runtime framework dependency and align
with the constitution.

**Alternatives considered**:

- Scaffold the entire app through shadcn: rejected because Next.js setup is already required and the
  product experience should not become a generic component demo.
- Build every primitive from scratch: rejected where an accessible generic primitive already solves
  the need without shaping the game board.

**Source**: https://ui.shadcn.com/docs/installation/next

## 4. QR Code Rendering Without Token Leakage

**Decision**: Use the standard `qrcode` package inside a Node Route Handler to generate a standalone
SVG. The public page embeds `/games/{gameId}/leader-qr`; that endpoint loads the token on the server
and returns only SVG path data with `Cache-Control: private, no-store`. Use the widely adopted ZXing
implementation through `@zxing/browser` to decode generated QR images in automated tests.

**Rationale**: The visible QR is the intentional casual bearer link, equivalent to access to the
leader card in the physical game. A byte-oriented server encoder keeps the token out of readable
public props, RSC application data, and client bundles. During implementation, `qrcode.react` could
not be rendered from a Next.js 16 Route Handler without unsupported React server-renderer imports or
duplicate React hook dispatchers. `qrcode` provides the same SVG result at the correct server
boundary. ZXing verifies the generated destination.

**Alternatives considered**:

- Client-render `QRCodeSVG`: rejected because its `value` prop would expose the token to public client
  data.
- Server-render `qrcode.react`: rejected after implementation validation because Next.js 16 blocks
  direct `react-dom/server` use in Route Handlers and alternate renderers produced hook mismatches.
- Show the private URL as text: rejected by the specification.

**Sources**:

- https://github.com/soldair/node-qrcode
- https://github.com/zpao/qrcode.react

## 5. Upstash Redis and TTL

**Decision**: Use `@upstash/redis` with `Redis.fromEnv()` and server-only
`UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`. Store a complete validated record under
`codename:game:{gameId}` using a single `SET` with `EX: 86400` so persistence and expiry are atomic.

**Rationale**: The HTTP client is designed for serverless and Next.js environments. Upstash supports
automatic key deletion after a timeout. A fixed 24-hour TTL is already settled in the feature spec;
reads must not extend it.

**Alternatives considered**:

- Server memory: rejected because Vercel instances are ephemeral and the constitution forbids it.
- Supabase or relational storage: rejected by MVP constraints and unnecessary for temporary records.
- Separate `SET` then `EXPIRE`: rejected because failure between commands could leave permanent data.
- Sliding TTL: rejected because the specification states revisits do not extend lifetime.

**Sources**:

- https://upstash.com/docs/redis/sdks/ts/overview
- https://upstash.com/docs/redis/howto/connect-with-upstash-redis
- https://upstash.com/docs/redis/sdks/ts/commands/generic/expire
- https://vercel.com/marketplace/upstash

## 6. IDs, Tokens, and Access Comparison

**Decision**: Generate `gameId` with `crypto.randomUUID()` and leader tokens with 32 random bytes
encoded as base64url. Treat the token as casual bearer access, compare exact values server-side,
never log it deliberately, and return one indistinguishable unavailable state for missing games and
invalid tokens.

**Rationale**: UUIDs provide independent public identifiers; 256 bits of randomness makes guessing
leader URLs impractical for the stated casual threat model. A uniform failure state avoids existence
leakage without adding authentication.

**Alternatives considered**:

- Sequential IDs or short codes: rejected because they are enumerable.
- User login or signed sessions: rejected as out of scope.
- Token hashing at rest: not selected because the QR must be reproducible for 24 hours; reversible
  storage or a second secret record would add complexity without improving the stated threat model.

## 7. Server Interaction Style

**Decision**: Use a Server Action for game creation, Server Components for public/leader page loads,
and one Route Handler for QR SVG output. Do not add a general JSON API in the MVP.

**Rationale**: These are native App Router boundaries and minimize publicly callable interfaces. The
creation action can validate form input, persist, and redirect without returning a token. Direct
server loaders keep secret projections off the client.

**Alternatives considered**:

- REST endpoints for every operation: rejected because no external client requires them.
- Client-side fetching: rejected because it broadens secret exposure and loading complexity.
- WebSockets: rejected because there is no realtime behavior.

## 8. Testing and Formatting

**Decision**: Use Vitest 4 with V8 coverage for pure and persistence-boundary tests, Playwright for a
small set of end-to-end flows, ESLint from Next.js, and Prettier with the Tailwind plugin.

**Rationale**: Vitest has a low-friction TypeScript workflow and Node 20+ support. Playwright covers
Chromium, Firefox, and WebKit and supports current Node LTS releases, making it suitable for desktop
and mobile viewport validation. Prettier complements ESLint for deterministic formatting.

**Alternatives considered**:

- Jest: valid, but Vitest is simpler for isolated ESM TypeScript modules and fast unit feedback.
- Cypress: valid, but Playwright provides direct multi-browser coverage with one tool.
- Full browser/component testing from day one: rejected; browser coverage remains limited to critical
  journeys while pure logic receives deeper unit coverage.

**Sources**:

- https://vitest.dev/guide/
- https://playwright.dev/docs/intro

## 9. Vercel Deployment

**Decision**: Deploy the root Next.js project to Vercel with Node.js 24 selected, connect an Upstash
Redis database through the marketplace or set the two REST environment variables manually, and run
the standard `next build`. Preview and production environments use separate Redis databases when
practical.

**Rationale**: Vercel is the required target and its Upstash integration injects the required
environment variables. Separate data stores prevent preview traffic from contaminating production.

**Alternatives considered**:

- Custom Node server: rejected because the App Router and Upstash HTTP client run directly on Vercel.
- Shared preview/production database: acceptable for an initial manual preview, but not preferred
  because test games would share the same namespace and quotas.

**Source**: https://vercel.com/marketplace/upstash

Vercel currently lists Node.js 24.x as its default runtime:
https://vercel.com/docs/functions/runtimes/node-js/node-js-versions
